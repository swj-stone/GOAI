# CampusMatch 大众低门槛版改版设计规格

版本：v2.0-design

确认日期：2026-08-14

状态：产品定位、PPT 结构和工程材料结构已由用户确认；本文件用于实施前复核。

## 1. 改版目标

本次改版不是删除技术能力，而是把技术复杂度放到系统内部，让不同专业、不同数字技能水平的学生都能完成求职准备。产品对用户使用自然语言，对评委和开发者保留 AgentTeams、Skill、数据契约、审计与可观测性设计。

改版必须同时满足以下目标：

1. 主 Demo 不依赖 Python、SQL、编程项目或复杂提示词。
2. 普通用户能用课程作业、社团活动、志愿服务、获奖记录和日常办公经历建立能力画像。
3. PPT 中专业概念首次出现时解释“是什么、为什么需要、用户得到什么”。
4. 除作品简介和 PPT 外，所有文件必须能直接指导开发、测试和验收。
5. 保留证据约束、隐私保护、公平审查、人工审批和完整运行记录。
6. 不把材料缺失等同于能力缺失，不把匹配度描述为录用概率。

## 2. 目标用户与市场边界

### 2.1 首要用户

- 没有正式实习或技术项目的在校学生。
- 不熟悉简历写作、招聘术语和 AI 提示词的学生。
- 需要同时服务大量学生的高校就业老师。

### 2.2 可扩展用户

- 首次求职者和跨专业求职者。
- 计划跳槽但不清楚能力迁移方式的职场人士。
- 只想了解岗位、尚未准备投递的职业探索者。
- 职业培训机构、校招平台和高校就业中心。

### 2.3 产品边界

系统提供材料整理、岗位解释、证据匹配和求职辅导，不执行以下动作：

- 不替用户虚构项目、职责、成果或数据。
- 不自动替用户投递岗位。
- 不替企业作录用或淘汰决定。
- 不依据性别、民族、宗教、健康状况等敏感属性排序。
- 不进行心理或医学诊断。

## 3. 主 Demo 场景

### 3.1 人物

合成用户“林晓雨”，非技术专业在校学生，没有正式实习，计划申请综合运营实习。

### 3.2 可提交材料

1. 课程小组汇报：协调 5 人分工、整理汇报提纲并完成课堂展示。
2. 社团活动：制作报名表、维护 Excel 名单、通知参与者并协助现场签到。
3. 志愿服务：负责访客引导、信息解答和临时排班调整。
4. 基础工具：使用 Word、Excel、PowerPoint 完成课程和活动任务。
5. 用户可补充或确认的信息：本人具体承担的工作、是否独立完成、是否允许写入简历。

所有数字和职责必须先出现在合成材料中，系统才能在建议或简历中使用。

### 3.3 目标岗位

综合运营实习生的合成 JD 包含：

- 硬性要求：沟通表达、基础文档写作、Excel 基础操作。
- 加分项：活动支持、内容发布、用户反馈整理。
- 模糊描述：“抗压能力强”“有主人翁意识”。
- 风险条件：“女性优先”等与工作职责无直接关系的限制。

Job Agent 必须把模糊描述转换为可询问的行为问题，把风险条件标记为“不参与匹配”，不得作为学生扣分项。

### 3.4 预期结果

| 岗位要求 | 状态 | 依据或处理 |
|---|---|---|
| 沟通表达 | 符合 | 课堂展示、志愿服务答疑 |
| 文档写作 | 部分符合 | 有汇报提纲，缺少正式运营文案 |
| Excel 基础 | 符合 | 社团报名名单维护 |
| 活动支持 | 符合 | 报名、通知、签到经历 |
| 内容发布 | 缺少证据 | 材料未说明发布过公众号或平台内容 |
| 性别限制 | 风险排除 | 不参与匹配，转人工确认岗位合规性 |

Coach 可以建议补充材料、优化表达、学习内容排版和准备面试，但不能把“协助签到”改写成“独立策划大型活动”。

## 4. 大众化产品语言

用户界面优先使用自然语言，技术字段仅用于后台、开发文档或可展开的“技术详情”。

| 用户可见名称 | 内部名称 | 首次出现时的解释 |
|---|---|---|
| 材料整理助手 | Profile Agent | 从用户提交的真实材料中整理经历和能力，每项结论都能回到原文 |
| 岗位解读助手 | Job Agent | 把招聘术语拆成硬性要求、加分项、模糊描述和风险条件 |
| 匹配分析助手 | Match Agent | 逐项比较岗位要求和已有证据，说明符合、部分符合或缺少证据 |
| 求职辅导助手 | Coach Agent | 基于已确认经历提出简历、学习和面试建议，不创造新经历 |
| 安全检查助手 | Audit Agent | 检查虚构、隐私、公平风险和导出条件，不通过时阻止导出 |
| 任务协调助手 | Career Navigator | 安排其他助手的执行顺序，保存进度并在失败时重试或请人处理 |
| 材料覆盖度 | evidence coverage | 当前材料覆盖了多少岗位要求，不代表个人能力上限 |
| 运行记录 | Trace | 保存系统做过什么、使用了什么证据和为什么得出该结论 |

## 5. 用户体验

### 5.1 四步主流程

1. 提交材料：上传 PDF/DOCX/图片，粘贴文字，或使用空白引导表单。
2. 选择目标：选择求职、跳槽或职业了解，并粘贴一个岗位 JD。
3. 确认经历：系统生成经历卡片；用户逐条确认、修改或标记“不用于求职”。
4. 获取报告：查看岗位解读、证据匹配、缺证提醒、简历建议和面试准备，经安全检查后导出。

### 5.2 降低门槛的交互要求

- 首屏不得要求 API Key、代码、模型选择或提示词。
- 用户没有简历时，可以回答“做过什么、和谁合作、产生什么结果、有什么证明”四组问题。
- 每次只要求用户完成一个明确动作。
- 技术详情默认折叠，错误信息同时提供自然语言解释和内部错误码。
- 允许跳过非必要字段；系统把结果标记为“材料不足”，而不是推断用户不会。
- 所有涉及写入简历或导出的新增事实必须由用户确认。

### 5.3 空材料起步

如果用户没有可上传文件，Navigator 创建四类引导问题：

1. 课程中完成过哪些个人或小组任务？
2. 社团、志愿服务或兼职中承担过哪些具体工作？
3. 使用过哪些日常工具完成这些工作？
4. 哪些老师、同学、记录或作品可以证明？

回答先保存为“用户陈述”，只有用户确认后才能作为简历建议依据；未经外部材料证明的内容必须显示“本人确认，未上传附件”。

## 6. 匹配规则

### 6.1 用户状态与内部状态映射

| 用户状态 | 内部状态 | 计分系数 |
|---|---|---:|
| 符合 | `MATCH` | 1.0 |
| 部分符合 | `PARTIAL` | 0.6 |
| 缺少证据 | `NO_EVIDENCE` | 0.0 |
| 能力待提升 | `GAP` | 0.0 |
| 信息冲突 | `CONFLICT` | 0.0，并要求人工确认 |
| 风险排除 | `POLICY_EXCLUDED` | 不进入分母和分子 |

`NO_EVIDENCE` 只表示当前材料不能支持判断；`GAP` 只有在用户明确表示不会、测试未通过或材料显示相反事实时才能使用。

### 6.2 默认权重

综合运营实习的合成示例采用：

- 沟通表达：25%。
- 文档写作：20%。
- 办公与信息处理：20%。
- 活动执行与协作：20%。
- 内容与用户意识：15%。

权重由 Job Agent 根据岗位要求归一化，Audit 检查总和必须为 100%。风险条件移除后，其权重不得转移给敏感属性，只能在剩余合法要求之间重新归一化。

### 6.3 两个独立指标

证据匹配度：

```text
match_score = Σ(合法要求权重 × 状态系数)
```

材料覆盖度：

```text
coverage = Σ(存在有效证据的合法要求权重)
```

合成手算示例：沟通 25 分、文档写作 20×0.6=12 分、Excel 20 分、活动支持 20 分、内容发布 0 分，证据匹配度为 77 分；前四项都有材料，材料覆盖度为 85%。两个数值都不代表录用概率。

### 6.4 模式差异

- 求职模式：强调当前岗位证据、简历修改和面试准备。
- 跳槽模式：强调可迁移能力、成果证明和经历边界。
- 职业了解模式：不生成投递结论，只解释工作内容、典型要求和探索路径。

MVP 实现求职模式；另外两种模式保留接口和示例，不在初版承诺完整功能。

## 7. 安全与人工介入

### 7.1 必须阻断的情况

- 建议出现材料和用户确认均未支持的新事实。
- 使用敏感属性参与排序或评分。
- 未获授权处理或导出个人信息。
- 运行记录缺失，无法确定建议依据。
- 输出包含违法有害内容或明显隐私泄露。

### 7.2 必须转人工的情况

- 材料之间互相冲突。
- 岗位条件可能违法或存在歧视，但规则不能确定。
- 用户不同意系统提取的关键经历。
- 情绪表达出现自伤或伤害他人的紧急风险信号。

系统不作医学诊断。紧急风险场景只提供简短支持、建议联系身边可信人员或当地紧急服务，并展示部署地区配置的官方联系方式；号码不得由模型生成，也不得用通用励志语录代替危机处置。

### 7.3 导出审批

导出前必须满足：用户授权有效、重要结论存在证据引用、无未处理冲突、Audit 为 `PASS`、用户确认最终版本。任一条件不满足时，报告只能保存为草稿。

## 8. Agent 与数据流

### 8.1 组件边界

- Navigator 负责目标、状态、重试和汇总，不修改 Worker 的专业判断。
- Profile 只整理用户材料，不解析岗位。
- Job 只解析岗位，不评价学生。
- Match 只比较结构化画像和岗位要求，不生成新经历。
- Coach 只基于确认材料提出建议。
- Audit 可以阻断输出，其他 Agent 不得覆盖其安全拒绝。

### 8.2 数据流

```text
用户授权
→ 原文件或引导表单
→ 可读文本与材料区块
→ 用户确认的经历卡片
→ 岗位要求分类
→ 逐项证据匹配
→ 简历、学习和面试建议
→ 安全审计
→ 人工确认
→ 报告与运行记录
```

大文件通过引用传递，Agent 之间只交换任务编号、结构化摘要和产物地址。原文件保持只读，任何修订产生新版本。

### 8.3 错误处理原则

- 文件无法解析：允许粘贴文本或填写表单，不终止整条任务。
- 关键字段缺失：进入 `NEEDS_INPUT`，向用户提出单一明确问题。
- 工具临时失败：同一幂等键最多重试两次，然后切换离线规则或转人工。
- 数据契约错误：拒绝进入下一状态，记录字段路径和校验错误。
- 审计未通过：进入 `BLOCKED`，返回可操作的修改项。
- 外部服务不可用：保留草稿和本地运行记录，不展示虚假的成功结果。

## 9. 16 页 PPT 结构

| 页码 | 页面任务 | 必须解释的内容 |
|---:|---|---|
| 1 | 封面 | 产品定位与面向大众的价值 |
| 2 | 真实场景 | 普通学生没有实习但有可转化经历 |
| 3 | 普遍问题 | 学生、学校和岗位信息三方痛点 |
| 4 | 现有 AI 不足 | 缺证、能力差距和岗位风险不能混成黑盒分数 |
| 5 | 产品是什么 | 五个用户可理解的助手及其结果 |
| 6 | 四步流程 | 不写代码、不学提示词即可使用 |
| 7 | 可用材料 | 文件上传和空材料起步两条入口 |
| 8 | 证据识别 | 原文、能力、证据三者关系及用户确认 |
| 9 | 岗位翻译 | 硬性、加分、模糊和风险条件 |
| 10 | 匹配结果 | 各状态、证据匹配度和材料覆盖度 |
| 11 | 求职辅导 | 原句、建议、依据、学习与模拟面试 |
| 12 | 安全审计 | 虚构数字和风险岗位条件的阻断流程 |
| 13 | Agent 协作 | 普通名称、技术名称以及分工必要性 |
| 14 | Skills 与工具 | 输入、动作、输出、失败处理和替代路径 |
| 15 | Demo 与实施 | 正常流程、异常流程和当前完成度边界 |
| 16 | 市场与开放 | 跨专业覆盖、机构价值和开放内容 |

每页遵循“用户问题—系统处理—实际价值”结构；专业术语首次出现时必须附中文解释。技术细节可以放在页面下半部或演讲者备注，但不能只列名称。

## 11. 测试策略

### 11.1 必测路径

1. 文件上传成功并生成可确认经历卡片。
2. 没有文件时通过引导表单完成画像。
3. 综合运营 JD 正确拆分四类要求。
4. 证据匹配度手算结果为 77，材料覆盖度为 85%。
5. 内容发布被标记为“缺少证据”，不变成“能力待提升”。
6. 性别条件被标记为风险排除且不参与分数。
7. Coach 生成“提升 30%”时被 Audit 阻断。
8. 文件解析失败时可切换粘贴文本。
9. 未经用户确认不得导出最终报告。
10. 紧急风险联系方式从地区配置读取，配置缺失时只提示联系当地紧急服务，不生成号码。

### 11.2 验收证据

每个测试保存输入夹具、实际输出、预期输出、运行记录和通过/失败结果。PPT 中仅展示合成示例；只有运行测试后才能把目标指标更新为实测结果。

## 12. 实施范围

### 12.1 MVP

- 求职模式。
- 综合运营一个主岗位族。
- 文件上传、粘贴文本和空材料表单。
- 六类 Agent 的离线确定性编排。
- 证据匹配、Coach 建议、Audit 阻断和人工导出。
- 固定合成数据和自动测试。

### 12.2 复赛增强

- AgentTeams 在线 Manager–Workers 协作。
- 多岗位词典和岗位库适配器。
- 模拟面试多轮记录。
- 可观测平台、部署脚本和完整评测。

### 12.3 不纳入本轮

- 自动投递。
- 企业端自动筛选。
- 真实高校生产部署。
- 跳槽和职业了解模式的完整实现。
- 未经合规验证的心理健康判断。

## 13. 成功标准

- 非技术专业学生无需代码和提示词即可走完主流程。
- 主 Demo 的每项能力都能回到课程、社团或志愿服务原文。
- PPT 16 页与讲稿、报告、Demo 数据相互一致。
- 每个 Agent 和 Skill 都有明确接口、失败处理和验收条件。
- 匹配公式可手算复核，风险条件不进入评分。
- 无证据经历无法通过 Audit 和导出审批。
- 所有目标指标明确标注“目标”“合成测试”或“真实试点”之一。
- 临时文件、真实个人数据和凭据不进入提交包。

## 14. 实施前决策结论

本规格采用“大众主线＋专业技术层”的单主线方案。主 Demo 使用非技术专业学生申请综合运营实习；Python/SQL 仅保留为扩展岗位示例。PPT 采用 16 页结构，工程材料按可开发、可测试、可验收标准补齐。后续实施不得重新把技术岗位设为默认示例，也不得为扩大功能范围而削弱证据、安全和人工审批要求。
