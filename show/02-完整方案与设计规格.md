# CampusMatch——高校可信求职协同基座

版本：初赛设计规格 v1.0
日期：2026-08-14
状态：方案已确认；等待书面评审后进入 Demo 实现计划

## 1. 执行摘要

CampusMatch 是面向高校就业服务中心的证据驱动多 Agent 基础设施。它不把“推荐岗位”简化成一个不可解释的分数，而是让每项学生能力、岗位要求、匹配状态、辅导建议和风险结论都能回到原始材料中的证据位置。

系统以 AgentTeams 的 Manager–Workers 架构为协同基点。Career Navigator 作为 Manager 对接学生或就业老师，Profile、Job、Match、Coach、Audit 五类 Worker 分工处理材料、要求、匹配、辅导和审计。Skills 是稳定的任务能力抽象；文件解析器、岗位库、知识库、报告导出和日志系统通过 MCP 或等价工具契约接入。

最终交付不是一次聊天，而是一份可审核的求职任务包：岗位推荐列表、证据矩阵、匹配可视化、能力缺口、简历建议、面试准备、审计报告和完整 Trace。系统只提供辅助决策，不自动投递、不替企业淘汰候选人，也不生成不存在的经历。

## 2. 真实场景与价值

### 2.1 场景背景

教育部披露，2026 届全国普通高校毕业生规模预计达到 1270 万人，并持续强调高校提供专业化、精准化就业服务。高校就业中心通常同时面对大量学生材料、企业岗位和个性化辅导请求，人工逐份阅读和持续跟进成本高。[教育部相关报道](https://www.moe.gov.cn/jyb_xwfb/s5147/202606/t20260615_1440719.html)

另一方面，招聘服务必须处理个人信息、虚假招聘和歧视性岗位条件。人力资源社会保障部与中央网信办要求强化求职者个人信息保护，并加强对含性别、年龄、学历等歧视性内容招聘信息的监管。[人力资源市场规范管理通知](https://app.www.gov.cn/govdata/gov/202408/29/518774/article.html)

### 2.2 典型用户

- 学生：希望找到适合的岗位，但难以判断“我是真的不匹配，还是简历没有写出证据”。
- 高校就业老师：需要为大量学生提供一致、可解释、可追踪的辅导。
- 高校就业中心管理员：需要配置岗位来源、政策、审计规则和数据权限。
- 企业校招合作方：希望岗位要求被准确理解，但不能让系统基于敏感属性筛选学生。

### 2.3 当前痛点

1. 学生信息散落在简历、成绩单、课程、项目和竞赛材料中，描述粒度不一致。
2. 岗位 JD 混合硬性要求、加分项、宣传用语和潜在歧视性条件。
3. 常见匹配工具只给分数，无法展示结论依据和不确定性。
4. 生成式 AI 容易把建议写成事实，甚至为简历补造项目成果。
5. 就业老师无法回放 AI 做了什么、为什么推荐、哪里需要人工确认。

### 2.4 可感知价值

- 对学生：把“匹配分”变成“证据＋缺口＋行动计划”。
- 对老师：用一致流程完成初筛与辅导，把时间留给复杂个案。
- 对学校：形成可审计、可复用、可评价的就业服务能力。
- 对生态：将材料解析、证据匹配、审计等能力沉淀为可独立复用的 Skills。

## 3. 产品范围

### 3.1 初赛与首个 Demo 范围

首个完整场景聚焦“在校大学生申请实习或校招岗位”：

1. 学生授权并上传一份简历和项目说明。
2. 系统生成可共同查看的 Markdown 与结构化能力证据。
3. 系统导入 5–10 个脱敏或合成岗位 JD。
4. 输出前三个岗位、匹配证据、能力缺口和置信度。
5. 生成简历修改与面试准备建议。
6. Audit Agent 拦截一条无证据的虚构成果或歧视性 JD 条件。
7. 学生或老师确认后导出求职报告。

### 3.2 后续可复用模式

- 应届求职：重视课程、项目、竞赛、实习与学习能力。
- 社招跳槽：重视工作成果、行业经验和可迁移能力。
- 职业了解：介绍职责、能力地图和学习路径，不进行强匹配。

三个模式复用相同证据模型与 Skill，只调整权重、提问策略和输出模板。

### 3.3 明确不做

- 不自动海投、不代替用户发送简历或邮件。
- 不根据性别、民族、宗教、籍贯、婚育等敏感属性排序。
- 不替企业作出录用、淘汰或薪酬决定。
- 不将“简历未出现证据”等同于“用户没有能力”。
- 不诊断抑郁症等医学状态；危机信号只触发安全升级与求助资源。
- 初版不覆盖招聘、培训、入职和绩效的完整人力资源生命周期。

## 4. 系统目标与成功标准

### 4.1 产品目标

在一个可回放任务中，证明多 Agent 能可靠完成：任务理解、材料结构化、岗位规范化、证据匹配、辅导生成、结果审计、人工审批和经验沉淀。

### 4.2 工程目标

- 至少 6 个清晰身份，其中 1 个 Manager、5 个 Worker。
- 核心能力以 Skill 形式封装，定义输入、输出、失败处理与安全边界。
- 每项重要结论包含 `evidence_refs` 或明确标注“缺少证据”。
- 高风险输出进入 `APPROVAL_PENDING`，不得直接导出。
- Trace 能关联 Agent、Skill、工具、模型、证据和审计事件。
- 离线模式无需真实个人信息和商业岗位接口即可复现。

### 4.3 目标指标（不是当前实测结果）

| 指标 | 首个 Demo 目标 | 验证方式 |
|---|---:|---|
| 重要结论证据覆盖率 | 100% | 检查所有匹配与修改建议是否带证据或缺证标记 |
| 虚构经历放行率 | 0% | 注入无证据成果，必须被 Audit 阻断 |
| 歧视条件进入评分率 | 0% | 注入歧视性 JD 字段，必须隔离且不计分 |
| 完整任务成功率 | ≥90% | 固定样例重复运行 20 次或离线确定性运行 |
| Tool 调用成功率 | ≥95% | Trace 统计成功/失败/重试 |
| 人工审批覆盖率 | 100% | 导出前必须记录审批事件 |
| 离线复现时间 | ≤10 分钟 | 从安装依赖到看到固定结果 |

## 5. 总体架构

### 5.1 分层架构

```text
学生 / 就业老师 / 管理员
            │
            ▼
Career Navigator（AgentTeams Manager）
目标识别｜同意与授权｜任务拆解｜结果汇总｜人工审批
            │ Matrix 房间 / 共享任务信封
 ┌──────────┼──────────┬──────────┬──────────┐
 ▼          ▼          ▼          ▼          ▼
Profile    Job        Match      Coach      Audit
Worker     Worker     Worker     Worker     Worker
 └──────────┴──────────┴──────────┴──────────┘
            │ Skills
            ▼
文档解析｜岗位规范化｜证据匹配｜差距规划｜模拟面试｜审计｜导出
            │ MCP / 等价工具契约
            ▼
文件/OCR｜岗位库｜政策库/RAG｜对象存储｜SLS/Trace｜报告导出
```

AgentTeams 官方采用 Manager–Workers 架构，并通过 Matrix 房间提供透明协作与人工介入能力；Worker 不持有真实凭据，外部调用可经 Higress 网关治理。[AgentTeams 官方项目](https://github.com/agentscope-ai/AgentTeams)

### 5.2 最小部署拓扑

- AgentTeams：编排 Manager 与 Workers，保存可观察的协作过程。
- Matrix/Element：人机协作、人工介入与 Demo 观察入口。
- MinIO/本地目录：保存原文件、Markdown、JSON、报告和评测证据。
- Higress：模型、MCP 与外部 API 的统一鉴权、限流和审计入口。
- SQLite（Demo）/PolarDB PostgreSQL（生产规划）：结构化状态、向量索引和审计元数据。
- OpenTelemetry＋本地 JSONL（Demo）/AgentLoop 或 SLS（生产规划）：Trace、Log、Metrics。

### 5.3 为什么不是“六个 Agent 一起聊天”

每个 Worker 只接收完成任务所需的最小上下文，并产出结构化结果。大文件通过 `artifact_ref` 传递，不在多轮对话中重复复制；重要结论用 `evidence_ref` 关联原始材料。Career Navigator 只负责任务路由和面向用户的汇总，不参与每次 Worker 内部推理。

## 6. 端到端状态机

```text
RECEIVED
  → CONSENTED
  → PARSED
  → PROFILE_GROUNDED
  → JOBS_NORMALIZED
  → MATCHED
  → COACHED
  → AUDITED
  → APPROVAL_PENDING
  → EXPORTED
```

异常状态：

- `NEEDS_INPUT`：关键材料缺失或 OCR 置信度过低，向用户提问。
- `RETRYING`：模型、工具或网络暂时失败，按幂等键有限重试。
- `BLOCKED`：发现虚构经历、未授权敏感信息或明确有害输出。
- `ESCALATED`：规则冲突、危机信号或高风险边界需要人工处理。
- `DEGRADED`：外部服务不可用，退化为离线规则或缓存结果。

## 7. 详细业务流程

### 7.1 目标与授权

Career Navigator 收集用户目标、求职阶段、岗位偏好、可处理材料范围和导出授权。默认只处理用户主动上传的材料。电话、住址、证件号等非匹配必需字段先脱敏，再进入 Worker 流程。

### 7.2 文档规范化

系统保留三层数据：

```text
原始文件（只读、带 SHA-256）
    → 带行号 Markdown（用户与 Agent 共同查看）
    → 结构化 JSON（能力、经历、证据引用、置信度）
```

Markdown 只是可读中间层，不能替代原始文件。每个证据引用至少包含 `document_id`、行号或区块 ID、原文片段和文件哈希。

### 7.3 学生画像

Profile Agent 抽取教育、课程、项目、工具、语言和求职偏好。抽取结果不直接写入长期画像：先由 Audit Agent 检查证据覆盖，再由用户确认。没有证据的能力进入 `unverified_claims`，不能作为匹配依据。

### 7.4 岗位规范化

Job Agent 将 JD 拆成：

- 合法、客观的硬性要求；
- 加分项；
- 工作职责；
- 模糊或宣传性描述；
- 可能歧视或不应参与评分的条件；
- 岗位领域、地点、方式、时间和发展路径。

### 7.5 可解释匹配

Match Agent 逐条比较岗位要求与学生证据，状态限定为：

- `MATCH`：证据直接支持要求；
- `PARTIAL`：存在相关证据，但深度或范围不足；
- `NO_EVIDENCE`：材料没有足够证据，不代表用户一定不会；
- `CONFLICT`：材料明确显示不满足合法硬性要求；
- `POLICY_EXCLUDED`：要求存在歧视或安全风险，不进入评分。

应届求职模式采用可配置五维权重：专业技能 30%、项目经历 20%、工具能力 15%、协作表达 15%、岗位偏好 20%。匹配度与置信度分开显示：匹配度回答“现有证据与岗位有多契合”，置信度回答“材料是否足够支撑这个判断”。

### 7.6 辅导与模拟面试

Coach Agent 只能基于已确认事实提供：

- 简历结构和措辞修改建议；
- 需要补充证据的问题；
- 分阶段学习计划；
- 针对岗位的面试准备清单；
- 一轮模拟面试与回答反馈。

模拟面试发现的新经历不得自动写入画像。系统提取候选证据，要求用户确认并补充来源，再重新计算匹配。

### 7.7 审计、审批与导出

Audit Agent 在关键阶段执行两类门禁：

- 前置审计：授权、最小必要数据、JD 歧视风险、工具权限和高风险动作。
- 后置审计：经历虚构、事实/建议混淆、证据缺失、隐私泄露、有害内容、Trace 完整性。

导出是有副作用的最终动作。只有 `audit_status=PASS` 且存在人工审批记录时，系统才生成 PDF/Markdown 求职报告。

## 8. 数据与接口设计

### 8.1 共享任务信封

```json
{
  "task_id": "task-20260814-001",
  "user_mode": "campus_job_search",
  "goal": "寻找数据分析实习",
  "consent_scope": ["resume", "project_notes"],
  "artifact_refs": ["artifact://resume/sha256-..."],
  "evidence_refs": [],
  "constraints": {"city": ["上海", "杭州"], "no_auto_submit": true},
  "risk_level": "medium",
  "trace_parent": "trace-001",
  "expected_output_schema": "match_report.v1"
}
```

### 8.2 证据对象

```json
{
  "evidence_id": "E-S001-003",
  "source_id": "student-materials",
  "source_type": "club",
  "line_start": 8,
  "line_end": 8,
  "quote": "我使用 Excel 维护活动报名名单，核对参与者信息。",
  "claim": "具备办公与信息处理经验",
  "evidence_strength": "direct",
  "confirmed_by_user": true
}
```

### 8.3 Agent 标准输出

```json
{
  "status": "SUCCESS",
  "findings": [],
  "evidence_refs": ["E-S001-003"],
  "confidence": 1.0,
  "policy_flags": [],
  "next_action": "RUN_MATCH",
  "idempotency_key": "task-001-profile-v1"
}
```

### 8.4 版本策略

- Agent Identity 使用语义版本，例如 `profile-agent@1.0.0`。
- Skill Schema 单独版本化，例如 `evidence-match.v1`。
- Prompt、政策规则、模型和工具版本全部写入 Trace。
- 输出 Schema 的破坏性变更必须升级主版本；旧任务可回放但不可混写。

## 9. 可视化设计

### 9.1 学生可见视图

- 环形图：总体匹配度；旁边独立显示置信度。
- 五边形雷达图：专业技能、项目经历、工具能力、协作表达、岗位偏好。
- 要求矩阵：逐项显示符合、部分符合、缺少证据、冲突和已排除风险条件。
- 证据抽屉：点击能力或结论，定位到 Markdown 原文。
- 行动路线：按一周、一个月、三个月组织可执行建议。

### 9.2 就业老师视图

- 待确认任务、风险任务和材料缺失任务队列。
- 学生报告预览、证据覆盖率和审计状态。
- 人工批准、退回补充、纠正结论和备注。
- 不展示基于敏感属性的排名。

### 9.3 可视化约束

- “没有证据”使用空心或问号状态，不使用红色零分羞辱用户。
- 雷达图各维度必须同量纲、同范围，并提供文字解释。
- 不用总体分数替代逐条证据；图表是摘要，证据矩阵是决策依据。

## 10. 安全、伦理与合规

### 10.1 个人信息

依据《个人信息保护法》，系统采用明确同意、目的限定、最小必要、可撤回和访问控制。个人信息处理者应保证信息质量，避免因不准确或不完整对个人权益造成不利影响。[中国人大网法律全文](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)

Demo 仅使用脱敏或合成材料；真实部署时将联系方式、证件、住址等与能力证据分区存储。

### 10.2 招聘公平

- 敏感属性不进入匹配特征。
- 歧视性 JD 条件标记为 `POLICY_EXCLUDED`，不进入评分。
- 系统不作自动淘汰或录用决定。
- 对规则无法确定的条件升级给就业老师或合规人员。

### 10.3 幻觉与经历真实性

- 事实性句子必须关联 `evidence_ref`。
- 建议必须使用“建议、可考虑、需要补充”等表述，不能伪装成经历。
- 新发现经历必须由用户确认，不能由模拟面试自动写回。
- Audit Agent 对无证据的数字化成果、职位、证书和时间线冲突执行硬阻断。

### 10.4 情绪与危机边界

Career Navigator 可以调整沟通语气，但不进行医学诊断。一般焦虑提供任务拆解和支持性表达；明确自伤、伤人或危机信号触发 `ESCALATED`，暂停普通求职建议，根据用户所在地展示权威紧急帮助资源，并鼓励联系可信任的人和专业服务。相关资源必须在部署地区配置与定期核验，不能由模型临时编造号码。

### 10.5 内容安全口径

项目不承诺“消灭所有违法内容”。工程口径是：对已定义风险类别执行检测、隔离、记录、拒绝和人工升级；对不确定高风险结果默认不发布。

## 11. 可观测与运行证据

OpenTelemetry 语义规范提供统一的 Trace、Log、Metric 命名基础；系统规划记录 Agent 名称/版本、操作、模型、工具、耗时、Token、状态和评测结果。[OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/)

### 11.1 Trace

每个任务包含：

```text
task span
 ├─ navigator.plan
 ├─ profile.extract → tool.document_parse
 ├─ job.normalize
 ├─ match.evaluate
 ├─ coach.generate
 ├─ audit.precheck / audit.postcheck
 └─ export.report
```

### 11.2 Log

结构化记录：任务状态、失败原因、证据引用、策略命中、用户确认、审批和回滚事件。日志不得默认存储完整简历正文。

### 11.3 Metrics

- 端到端成功率和时延；
- Agent/Skill/Tool 成功率；
- Token 与调用成本；
- 证据覆盖率；
- 虚构经历拦截率；
- 人工退回率；
- 不同版本的回归评测结果。

阿里云官方 `alibabacloud-sls-query` Skill 可用于查询分析 SLS 日志；初版可先输出 JSONL，复赛再接入 SLS 查询和 AgentLoop。[阿里云 Skills 门户](https://skills.aliyun.com/skills/alibabacloud-sls-query)

## 12. 错误处理与降级

| 异常 | 检测 | 系统行为 | 用户可见信息 |
|---|---|---|---|
| 扫描 PDF 无法解析 | 文本为空/OCR 低置信 | 转 OCR；仍失败则 `NEEDS_INPUT` | 请上传清晰版本或手动补充 |
| JD 信息不足 | 必备字段缺失 | 标记不确定，Job Agent 请求补充 | 不强行生成精确分数 |
| 模型输出 Schema 错误 | JSON Schema 校验失败 | 同一幂等键重试一次，再降级规则模板 | 显示结果延迟或功能降级 |
| 工具超时 | 超时/5xx | 指数退避、有限重试、缓存或离线模式 | 不重复创建副作用 |
| Agent 结论冲突 | 同一要求状态不一致 | Audit 仲裁；证据不足则人工确认 | 展示冲突项和来源 |
| 无证据事实 | 缺少 evidence_ref | `BLOCKED`，退回 Coach/Profile | 不进入导出报告 |
| 歧视性要求 | 规则＋模型复核 | `POLICY_EXCLUDED`，不计分并记录 | 提示岗位信息风险 |
| 危机信号 | 明确语义规则＋模型复核 | `ESCALATED`，停止普通建议 | 展示经核验的地区求助资源 |

所有写操作使用 `idempotency_key`；导出前保存快照，错误时回滚到最近通过审计的版本。

## 13. 评测设计

### 13.1 固定数据集

构造 5 份合成学生材料、10 个合成岗位、50 条岗位要求，覆盖：直接匹配、部分匹配、缺证、合法硬性冲突、歧视性要求、OCR 失败和经历虚构。

### 13.2 自动评测

- Schema 校验：所有 Agent 与 Skill 输出必须通过 JSON Schema。
- 规则评测：证据引用存在、行号合法、文件哈希一致。
- 对照答案：逐条要求状态与人工标注一致。
- 安全注入：无证据数字、敏感信息、歧视条件必须被阻断或隔离。
- 回归测试：每次 Agent/Skill/Prompt 版本变化重新运行固定数据集。

### 13.3 人工评测

由学生或就业老师评价：结论是否可理解、建议是否可执行、证据是否可信、是否存在冒犯或过度推断。LLM-as-Judge 只作为辅助指标，不替代规则和人工证据核验。

## 14. Demo 实现边界

### 14.1 当前已实现的双链路展示

采用合成材料和双模式：

- 浏览器确定性链路：固定合成数据＋规则匹配＋Trace，非技术评委在浏览器中即可完成载入、分析、审批与导出；当前 50 项自动化测试通过。
- HiClaw Team 实机链路：Career Navigator 编排 Profile、Job、Match、Coach、Audit 五个专业阶段，六个 Worker 的 MCP 健康检查均通过，最终业务状态为 `READY`。
- 可选模型增强：后续可接 OpenAI-compatible 模型增强开放文本抽取与表达，但结果仍须通过 Schema、证据和 Audit 校验。

### 14.2 现场关键演示

1. 上传学生简历，展示原文与 Markdown。
2. 点击“Excel 信息整理”或“基础文档写作”，回到原文证据。
3. 导入岗位，展示环形图、雷达图和证据矩阵。
4. Coach 建议中故意出现“提升 30%”但材料无证据。
5. Audit Agent 阻止导出并指出缺失证据。
6. 用户删除虚构内容或补充真实证据，老师批准后导出。

### 14.3 已落地的 HiClaw / AgentTeams 映射

- Manager：Career Navigator。
- Team Room：Profile 与 Job 并行，Match、Coach、Audit 按依赖顺序推进；人工可在 Matrix 房间观察和干预。
- Workers：Profile、Job、Match、Coach、Audit。
- Shared File System：原文件、Markdown、JSON、报告。
- Higress：模型、MCP、云 Skill 的凭据代理和调用治理。
- Element：评委可进入房间查看、暂停和纠正任务。

## 16. 开放与复用计划

计划以 Apache-2.0 许可开放以下非敏感成果：

- Agent Identity 与协作任务信封规范；
- 核心 Skills、JSON Schema 和错误码；
- 合成学生/岗位数据与评测用例；
- MCP/工具适配器接口；
- 离线 Demo、部署说明和 Trace 示例；
- 招聘公平、证据覆盖和幻觉拦截规则模板。

真实个人数据、学校内部政策和商业岗位接口凭据不进入开源仓库。闭源模型通过兼容接口隔离，并保留本地/开源模型迁移路径。

## 17. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 项目过度扩张 | Demo 不完整 | 首个场景只做大学生实习/校招 |
| 匹配分被误当录用概率 | 误导用户 | 匹配度、置信度、证据矩阵分开展示 |
| LLM 虚构经历 | 损害诚信 | 事实必须带 evidence_ref；Audit 硬阻断 |
| 招聘歧视被算法放大 | 合规与公平风险 | 敏感属性隔离；风险条件不计分；人工升级 |
| 简历隐私泄露 | 严重安全风险 | 最小必要、脱敏、分区存储、网关凭据治理 |
| AgentTeams 部署复杂 | 复现失败 | 离线确定性模式＋锁定版本＋一键脚本 |
| 缺乏真实高校数据 | 价值证据不足 | 初赛用官方政策与合成数据，复赛争取老师访谈 |

## 18. 设计决策总结

CampusMatch 的核心竞争力不是“更多 Agent”，而是把每个 Agent 的职责、证据、权限和失败边界工程化：

1. 以高校就业中心为组织级业务方，学生为前台用户。
2. 以证据链替代黑盒推荐，以置信度表达材料不足。
3. 以 Audit Agent 和人工审批防止虚构、歧视和隐私泄露。
4. 以 AgentTeams 承载透明协作、状态流转和人工介入。
5. 以可复用 Skill、契约和评测数据推动从 Demo 走向 Production。
